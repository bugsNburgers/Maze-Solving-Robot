## 0) One‑sentence summary
This project launches a Turtlebot3 Waffle robot in a Gazebo Classic maze world, runs the Nav2 stack to localize/plan on a pre-made map, and uses a Python script to set an initial pose + send a goal so the robot drives through the maze.

## 2) Plain English: what happens when you “run the project”
Think of this like a video game + autopilot:

1) **Gazebo Classic opens**
   - Gazebo is the simulator window.
   - The maze world is placed into an empty Gazebo world.
   - A Turtlebot3 robot model is spawned at a chosen starting position.

2) **RViz2 opens**
   - RViz is the visualization window.
   - It shows a *2D map*, robot pose estimate, laser scans, and Nav2 overlays.

3) **Nav2 stack starts**
   - Nav2 is the navigation brain.
   - It needs:
     - a map (a `.yaml` that references a `.pgm` image),
     - the robot’s sensors (laser scan),
     - transforms between frames (`map`, `odom`, `base_link`/`base_footprint`),
     - and an initial pose guess.

4) **maze_solver.py is run by you** (in a second terminal)
   - This script:
     - tells Nav2 “the robot starts here on the map” (initial pose),
     - then tells Nav2 “go to this goal location”.
   - Nav2 then publishes velocity commands (`/cmd_vel`),
     and the simulated robot moves.

## 3) Technical architecture (ROS 2 pieces and data flow)
### 3.1 Core external systems
- **Gazebo Classic**: physics simulation, robot model, world model.
- **gazebo_ros**: bridge layer for Gazebo <-> ROS 2 (spawn services, plugins).
- **turtlebot3_gazebo**: Turtlebot3 simulation assets + spawn launch files.
- **Nav2 (nav2_bringup)**: localization (AMCL), planning, control, recovery.
- **RViz2**: visualization.
- Optional mapping systems (present but disabled by default in the main launch):
  - **slam_toolbox** (recommended) or
  - **cartographer_ros** (configured via Lua).

### 3.2 Important ROS concepts used
- **Nodes**: running programs in ROS.
- **Topics**: streaming data channels (e.g., `/scan`, `/cmd_vel`).
- **Services**: request/response calls (e.g., Gazebo `/spawn_entity`).
- **Frames & TF**: coordinate transforms (`map`, `odom`, `base_link`, etc.).
- **use_sim_time**: simulation time comes from `/clock` instead of wall time.

### 3.3 Key topics you should expect
From earlier runtime inspection, typical topics include:
- `/cmd_vel` — velocity commands (Nav2 -> robot).
- `/scan` — LIDAR scans.
- `/odom` — odometry from simulated robot.
- `/tf`, `/tf_static` — transforms.
- `/amcl_pose` — pose estimate from AMCL.
- `/clock` — simulation time.

## 5) Timeline of what happened in this chat (what broke, why, fix)
This section is a factual log of events that occurred while setting the project up.

### 5.1 Initial launch failure: package not found
- Symptom:
  - `ros2 launch autonomous_tb3 tb3_maze_navigation.launch.py` failed with “Package 'autonomous_tb3' not found”.
- Root cause:
  - The workspace had not been built *in a way that made the package discoverable* in the current environment.
  - Also, `colcon build` was finishing with “0 packages finished”, which strongly indicates **colcon could not detect ROS packages**.

### 5.2 Colcon shows 0 packages: missing ROS discovery plugin
- Symptom:
  - `colcon build` and `colcon list` reported 0 packages.
- Root cause:
  - `colcon` was installed, but the ROS package discovery extension was missing.
- Fix:
  - Installed `python3-colcon-ros` (and its dependency `python3-colcon-cmake`).
  - After that, `colcon list --base-paths src` correctly showed:
    - `autonomous_tb3  (ros.ament_cmake)`

### 5.3 Launch failure: entity_spawner executable not found
- Symptom:
  - Launch error: executable `entity_spawner.py` not found in install libexec.
- Root cause:
  - CMake `install(PROGRAMS ...)` installs Python scripts as executables, but they must be **executable** on disk.
- Fix:
  - `chmod +x` on the Python scripts and rebuild.

### 5.4 Runtime conflict: Gazebo / entity already exists
- Symptom:
  - `gzserver` crashed and `spawn_entity` said “Entity [waffle] already exists”.
- Root cause:
  - stale Gazebo processes from previous runs.
- Fix:
  - kill stale `gzserver`, `gzclient`, `rviz2` processes and relaunch cleanly.

### 5.5 Robot not moving: AMCL / Nav2 activation issues + interrupt
There were two different failure modes:

1) **Earlier**: AMCL rejected initialpose as malformed and TF frames were missing.
   - Fix: updated `maze_solver.py` to publish a proper normalized quaternion and set `use_sim_time` for the navigator node.

2) **Later**: solver printed `amcl/get_state service not available`.
   - Root cause: Nav2 stack wasn’t fully active / got interrupted.
   - Confirmed by launch logs showing “user interrupted with ctrl-c (SIGINT)”.

### 5.6 Confirmed working
A clean run produced solver output:
- “Nav2 is ready for use!”
- “Navigating to goal …”
- ETA countdown decreasing.
That indicates Nav2 accepted initial pose, planned, and started commanding motion.

## 8) Scripts (ROS nodes) — function-by-function
### 8.1 `entity_spawner.py`
File: `src/autonomous_tb3/script/entity_spawner.py`
Role:
- Spawns a Gazebo entity (here: the maze world model) by calling the Gazebo ROS service `/spawn_entity`.

Imports:
- `gazebo_msgs.srv.SpawnEntity` — service type.
- `rclpy` — ROS 2 Python client library.

Functions:
- `main()`
  - Reads argv: `[sdf_path, model_name, x, y]`.
  - Initializes ROS with `rclpy.init()`.
  - Creates a node named `spawning_node`.
  - Creates a service client to `/spawn_entity`.
  - Waits for service readiness.
  - Fills a `SpawnEntity.Request()`:
    - `request.name` = model name.
    - `request.xml` = contents of SDF file.
    - `request.initial_pose.position.(x,y)` = spawn coordinates.
  - Calls the service asynchronously and spins until complete.
  - Prints the response.
  - Shuts down cleanly.

Behavior:
- If Gazebo isn’t running or the `/spawn_entity` service isn’t available, it will wait.
- If you spawn a model with the same name twice, Gazebo may reject it.

### 8.2 `maze_solver.py`
File: `src/autonomous_tb3/script/maze_solver.py`
Role:
- Uses Nav2 Simple Commander to:
  1) set the robot initial pose,
  2) wait for Nav2 to be active,
  3) send a goal pose,
  4) print ETA feedback.

Imports:
- `PoseStamped` — pose message.
- `BasicNavigator`, `TaskResult` — Nav2 Simple Commander API.
- `rclpy`, `Duration`, `Parameter`.
- `sin`, `cos`.

Functions:
- `main()`
  1) `rclpy.init()`
  2) Create `navigator = BasicNavigator()`
  3) Set sim time parameter on navigator node:
     - `use_sim_time = True`
  4) Build `initial_pose`:
     - `frame_id = 'map'`
     - position set to a hard-coded starting coordinate.
     - quaternion set using `sin/cos` (normalized) for yaw = 0.2 rad.
     - `navigator.setInitialPose(initial_pose)`
  5) `navigator.waitUntilNav2Active()`
  6) Build `goal_pose`:
     - `frame_id = 'map'`
     - position set to a hard-coded goal coordinate.
     - quaternion set similarly.
     - `navigator.goToPose(goal_pose)`
  7) Loop until task complete:
     - prints ETA every 5 feedback cycles.
  8) Print final result based on `TaskResult`.
  9) Shutdown nav2 lifecycle.

Important behavior / gotchas:
- If Nav2 isn’t running, it will wait.
- If AMCL never receives/accepts initial pose, Nav2 can’t localize and won’t drive.
- If your launch is killed (SIGINT), `amcl/get_state` will disappear and solver will wait forever.

### 8.3 `occupancy_grid_pub.py`
File: `src/autonomous_tb3/script/occupancy_grid_pub.py`
Role:
- Example publisher of `nav_msgs/OccupancyGrid` on topic `occupancy_grid_map`.

Classes:
- `Occupancy_Grid_Publisher(Node)`
  - `__init__()`:
    - creates publisher for OccupancyGrid.
    - creates timer at 0.5s.
  - `timer_callback()`:
    - constructs an OccupancyGrid.
    - fills header and basic metadata.
    - fills a fixed 3x3 array of occupancy values.
    - publishes.

Functions:
- `main(args=None)`
  - init, spin node, shutdown.

Notes:
- This is not used by the main maze navigation flow.
- It is a learning/demo node for understanding OccupancyGrid.

## 1. What This Project Does
This project simulates a TurtleBot3 Waffle in Gazebo Classic and makes it solve a procedurally generated maze autonomously.

The current implementation does all of this in one flow:
1. Generate a new random maze (fixed 21x21 grid) every launch.
2. Spawn the maze model dynamically into Gazebo.
3. Export a runtime occupancy map artifact for Nav2.
4. Launch Nav2 (static runtime map mode by default, optional SLAM mode).
5. Run a solver that computes shortest path on the known generated grid.
6. Execute that route directly with a stable odom-based controller.
7. Reach the red finish marker reliably.

## 2. Core Design Decisions
### 2.1 Procedural world, fixed size
- Maze topology randomizes each run.
- Grid dimensions stay fixed at 21x21 for predictable scale and tuning.

### 2.2 Runtime map artifacts
- Maze generation writes runtime files under /tmp/autonomous_tb3:
  - maze_runtime.json
  - maze_runtime_map.pgm
  - maze_runtime_map.yaml
- Nav2 consumes this generated map in use_slam:=false mode.

### 2.3 Route execution strategy (important)
Current solver strategy is deliberate:
1. Compute shortest path on generated grid (ground-truth corridor graph).
2. Execute direct route follower first (odom waypoint tracking).
3. Fall back to Nav2 segment goals only if direct execution fails.

Reason:
- In this maze type, pure Nav2 local control repeatedly oscillated/collision-checked in tight corridors.
- Direct route following removed excessive spin/recovery loops and stabilized completion.

Responsibilities:
1. Generate random 21x21 maze from maze_generator.generate_maze().

  - min_steps=35
  - max_steps=60
  - fallback: farthest safe interior cell
4. Build runtime payload JSON and map artifacts.
5. Build procedural SDF with wall collisions/visuals.

- seed
- height, width
- resolution, origin
- start_cell, goal_cell
- start_pose, goal_pose
- grid (0 free, 1 occupied)

## 5.3 Script: maze_generator.py
- Uses recursive backtracker-style carving on odd grid dimensions.
- Guarantees traversable corridors.
- Provides utility for farthest-cell search via BFS.
- Base dimensions in code:
  - MAZE_HEIGHT = 21
  - MAZE_WIDTH = 21

## 5.4 Script: maze_solver.py
Current behavior:
1. Wait for endpoint publishers and runtime payload.
2. Publish initial pose repeatedly to AMCL via /initialpose.
3. Compute shortest path over runtime grid.
4. Primary: direct route execution in odom frame:
  - nearest path index from current odom
  - waypoint tracking (rotate/drive combined)
5. Fallback: Nav2 segment execution if direct path fails.
6. Report success/failure with clear logs.

Notable functions:
- compute_shortest_path(): BFS shortest path.
- navigate_path_direct(): stable waypoint follower.
- navigate(): Nav2 action client path for fallback.
- navigate_path(): primary-direct then fallback-Nav2 orchestration.

File: config/tb3_nav_params.yaml

- AMCL base frame: base_link.
- Planner:
  - NavFn

- Controller:
  - Regulated Pure Pursuit

- Costmaps:
  - robot_radius: 0.08
  - inflation_radius: 0.10
  - cost_scaling_factor: 1.5

This config is tuned to avoid overly aggressive behavior while remaining stable in narrow maze passages.
